# Gatekeeper Specification

**Draft v0.1 (concept stage). Not implemented. Everything here may change.**

This document describes what a Gatekeeper implementation does and the data
formats it exchanges. It is written to be language-neutral. The key words
MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as described in
[RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and
[RFC 8174](https://www.rfc-editor.org/rfc/rfc8174) when, and only when, they
appear in capitals. Because this is a draft, normative statements express the
current design intent, not a stable contract. JSON examples are in
[examples/](examples/); JSON Schemas and test vectors are planned for v0.2.

## 1. Terms

- **Person**: the human whose data is stored on the device.
- **Host app**: the application that stores the person's data and embeds
  Gatekeeper.
- **Requester**: an AI agent or other software that asks questions,
  identified through its transport (e.g. an MCP client).
- **Gatekeeper**: the component specified here. It runs on the person's
  device, in or beside the host app.
- **Attribute**: one typed fact about the person (e.g. the expiry date of a
  residence permit).
- **Question**: a typed predicate over one attribute, asked by a requester
  for a stated purpose.
- **Policy**: access rules the person has consented to: which requester may
  ask which questions about which attributes, for which purpose, how often
  and until when.
- **Arbitration**: the deterministic decision Gatekeeper makes for one
  question: allow, generalise or refuse.
- **Disclosure**: the controlled result returned to the requester: a
  predicate result, a coarse range, or a refusal.
- **Audit log**: the tamper-evident, hash-chained record of every
  disclosure and every policy change.
- **Proof plugin**: an optional module that attaches verifiable evidence to
  a disclosure using an existing, audited library.

## 2. Data model

Gatekeeper never owns the data. The host app exposes attributes through an
attribute interface; Gatekeeper reads them only during arbitration.

An attribute has:

| Field | Meaning |
|---|---|
| `id` | Stable dotted name, e.g. `residence_permit.expiry_date`. |
| `type` | One of `boolean`, `integer`, `date`, `enum`. |
| `domain` | For `integer`: `min`, `max`. For `enum`: the closed list of values. For `date`: optional `min`, `max`. |
| `sensitivity` | One of `low`, `moderate`, `high`, `special` (`special` = special categories of personal data, e.g. health). |
| `source` | `self_declared`, `document_extracted` or `issuer_attested`. Informational; see § 10. |

Rules:

- D1. An attribute value MUST be of its declared type or absent. Free text
  is not an attribute type; host apps MUST map data to closed encodings
  (ISO 8601 dates, ISO 3166 country codes, enumerations) before exposure.
- D2. Identifiers that are unique to the person (document numbers, names,
  addresses) SHOULD NOT be exposed as attributes at all. If exposed, only
  `exists` (§ 3) is meaningful.
- D3. `sensitivity` sets defaults for arbitration (§ 5) and reconstruction
  protection (§ 8). A policy MAY be stricter than the default, never looser
  without an explicit consent step that names the relaxation.

## 3. Question model

The question language is deliberately small. Each question concerns exactly
one attribute. Small languages are what make reconstruction protection
tractable (§ 8).

```json
{
  "spec_version": "0.1-draft",
  "question_id": "<UUID v4, generated by the requester>",
  "requester_id": "<identity established by the transport>",
  "purpose_id": "job-application",
  "attribute": "residence_permit.expiry_date",
  "predicate": { "op": "gt", "operand": { "relative": "P6M" } }
}
```

Operators:

| `op` | Types | Meaning |
|---|---|---|
| `exists` | all | The attribute has a value. No operand. |
| `eq`, `ne` | all | Equality. |
| `lt`, `le`, `gt`, `ge` | `integer`, `date` | Comparison with one operand. |
| `between` | `integer`, `date` | `lower <= value <= upper`; operand `{ "lower": …, "upper": … }`. |
| `in` | `enum` | Membership; operand `{ "values": [ … ] }`. |
| `range` | `integer`, `date` | Asks for the coarse bucket containing the value (§ 6.3). No operand. |

Operands are either absolute (`{ "value": "2027-03-01" }`) or, for dates,
relative to the reference date (`{ "relative": "P6M" }`, an ISO 8601
duration). The reference date is chosen by Gatekeeper, not the requester
(§ 8, R3).

- Q1. A question that is malformed, names an unknown operator, or does not
  match the attribute type MUST be refused with reason `invalid_question`.
- Q2. Questions MUST NOT contain logical connectives (and, or, not) or
  refer to more than one attribute. Combining facts is the requester's job,
  and every component question is arbitrated and budgeted separately.
- Q3. The requester-supplied `purpose_id` is a claim. Gatekeeper cannot
  verify intent; it can only bind the answer to the purpose the person
  approved and record it (§ 10).

## 4. Policy model

A policy is created only through an explicit consent step in the host app's
UI. Requesters MAY propose a policy; they MUST NOT be able to activate one.

| Field | Meaning |
|---|---|
| `policy_id` | UUID v4. |
| `requester` | `id` and `binding` (how the identity is established, e.g. `mcp_oauth_client`), plus a display name for the consent UI. |
| `purpose` | `id` and a human-readable description shown at consent. |
| `rules` | One entry per attribute: allowed operators, allowed operands, disclosure type, generalisation, budget. |
| `global_limits` | Optional caps across all rules of this policy. |
| `granted_at`, `expires_at` | ISO 8601 timestamps. A policy without `expires_at` MUST NOT be accepted. |
| `consent` | How consent was given (e.g. `dialog`) and the policy text version shown. |

A rule contains:

- `attribute`: the attribute id.
- `allowed_ops`: subset of § 3 operators.
- `allowed_operands`: for comparisons, the closed list of operands the
  requester may use (e.g. `P3M`, `P6M`, `P12M`). For `high` and `special`
  attributes this list MUST be present; free operands MUST NOT be allowed.
- `disclosure`: `predicate` or `range`.
- `generalisation`: e.g. `date_granularity` (`day`, `week`, `month`,
  `quarter`, `year`) or integer `bucket_width`.
- `reference_date_granularity`: how coarsely "today" is rounded (§ 8, R3).
- `budget`: `max_questions` per `period` (ISO 8601 duration), counted per
  requester and attribute.

Rules:

- P1. At most one active policy per (requester, purpose) pair. A new
  policy for the same pair supersedes the old one; both events are logged.
- P2. Revocation by the person MUST take effect before the next
  arbitration and MUST be logged. Expiry is equivalent to revocation.
- P3. Anything not explicitly allowed by a rule is refused (default deny).
- P4. A policy is stored locally and is itself sensitive; the host app
  MUST store it with the same protection as the data.

## 5. Arbitration

Arbitration is a pure, deterministic function of: the question, the active
policies, the requester's question-and-disclosure history, the budget
counters, the reference date and, only in step 7, the attribute value. It
does not use a language model.

Gatekeeper MUST perform these steps in order and stop at the first refusal:

1. **Validate** the question (§ 3, Q1–Q2). Else refuse `invalid_question`.
2. **Find the policy** for (requester, purpose). None, expired or revoked:
   refuse `no_policy`.
3. **Match the rule** for the attribute, operator and operand. If the
   operand is not allowed but the rule defines a generalisation that maps
   it to an allowed operand *without depending on the data*, Gatekeeper
   MAY rewrite the question and mark the disclosure `generalised`. Else
   refuse `not_permitted`.
4. **Check the budget** (§ 8, R2). Exhausted: refuse `budget_exhausted`.
5. **Check overlap** against the requester's own history (§ 8, R4). Could
   reveal too much: refuse `overlap`.
6. **Charge the budget.** Every question that reaches this step is
   counted, whatever the outcome of step 7.
7. **Evaluate** the predicate against the attribute value. An absent value
   yields the answer `unknown`, which is part of every answer domain.
8. **Record** the audit log entry (§ 7). If writing the entry fails, no
   disclosure is returned (fail closed).
9. **Return** the disclosure (§ 6).

- A1. Steps 1–6 MUST NOT read the attribute value. Therefore every refusal
  depends only on information the requester already has or on the policy,
  and reveals nothing about the data (§ 8, R5).
- A2. Identical inputs MUST produce identical outputs. Implementations
  MUST pass the shared test vectors (planned).
- A3. There is no fallback. If any step fails unexpectedly, the outcome is
  a refusal, never raw data.

## 6. Disclosure formats

### 6.1 Answer

```json
{
  "spec_version": "0.1-draft",
  "disclosure_id": "<UUID v4>",
  "question_id": "<from the question>",
  "outcome": "answered",
  "answer": { "type": "predicate", "value": true },
  "answered_question": { "attribute": "…", "predicate": { "…": "…" } },
  "generalised": false,
  "reference_date": "2026-11-09",
  "valid_until": "2026-11-15",
  "proofs": []
}
```

- `value` is `true`, `false` or `"unknown"`.
- `answered_question` is the question actually evaluated (differs from the
  asked one only if `generalised` is `true`).
- `reference_date` is the rounded date relative operands were resolved
  against; `valid_until` is the end of that rounding window. Within it, the
  same question returns the same disclosure (§ 8, R3).

### 6.2 Refusal

```json
{
  "spec_version": "0.1-draft",
  "disclosure_id": "<UUID v4>",
  "question_id": "<from the question>",
  "outcome": "refused",
  "reason": "not_permitted"
}
```

- `reason` is one of `invalid_question`, `no_policy`, `not_permitted`,
  `budget_exhausted`, `overlap`. Each is decided before the data is read
  (A1). A Gatekeeper MAY collapse all reasons to `refused`.
- A refusal MUST NOT carry any other field, timing difference or error text
  that depends on the data.

### 6.3 Coarsening rules

- C1. Range answers use fixed bucket boundaries derived from the rule's
  `generalisation` alone (e.g. calendar quarters), never boundaries chosen
  around the actual value. Example: `{ "type": "range", "lower":
  "2027-04-01", "upper": "2027-06-30" }`.
- C2. Dates are reported no finer than the rule's `date_granularity`.
- C3. A disclosure MUST NOT contain the attribute value, a derived
  identifier, or the audit-log sequence number (which would reveal how many
  disclosures other requesters received).

## 7. Audit log

The audit log is an append-only list of entries, local to the device and
readable by the person through the host app.

Entry fields:

| Field | Meaning |
|---|---|
| `seq` | 0-based position in the log. |
| `timestamp` | ISO 8601, UTC. |
| `event` | `disclosure`, `refusal`, `policy_granted`, `policy_superseded`, `policy_revoked`, `policy_expired`. |
| `policy_id`, `requester_id`, `purpose_id` | As applicable. |
| `question` | Attribute, operator and operand, as asked and as answered. |
| `outcome` | The disclosure exactly as returned. Never the raw attribute value. |
| `prev_hash` | `entry_hash` of the previous entry; 64 hex zeros for `seq` 0. |
| `entry_hash` | SHA-256 over the [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) (JCS) canonical JSON of the entry without `entry_hash`, hex-encoded. |

- L1. Verification recomputes every `entry_hash` and checks every
  `prev_hash`. Any mismatch MUST be shown to the person as a broken log.
- L2. Implementations SHOULD periodically sign the latest `entry_hash`
  with a device Ed25519 key (libsodium) as a checkpoint, and MAY let the
  person export checkpoints off the device. Without an external anchor the
  log is tamper-evident only against parties that do not control the
  device.
- L3. The log reveals which requesters asked what; it is sensitive data
  and MUST be stored with the same protection as the attributes.
- L4. Log entries MUST NOT be deleted to free budget or hide activity. If
  retention limits require pruning, the pruned prefix is replaced by a
  signed checkpoint.

## 8. Reconstruction protection

### 8.1 Threat model

- The requester is adaptive and may be malicious: it chooses each question
  after seeing earlier answers, repeats questions over days, and may be
  steered by prompt injection.
- Several requesters may collude (e.g. different agents of one provider).
- Every disclosure is assumed to become known to the requester's whole
  stack, including the model provider.
- Trusted: Gatekeeper, the device operating system, the host app and its
  storage. Out of scope: a compromised device, physical side channels, and
  a person persuaded to consent to an overly broad policy (mitigated only by
  UI design and defaults).

The goal is not "no information leaks" (every answer leaks something) but a
*known, bounded* leak per attribute that the person approved.

### 8.2 Measures

- **R1 Closed question space.** For `high` and `special` attributes, the
  rule enumerates allowed operands (§ 4). With *k* allowed thresholds, all
  answers within one validity window together carry at most
  log2(*k* + 2) bits about the attribute (*k* + 1 intervals, plus
  `unknown`).
- **R2 Budgets.** Counted per (requester, attribute, period), and per
  (attribute, period) across all requesters to limit collusion. A refusal
  caused by a cross-requester budget reveals activity of other requesters
  (not data); implementations MAY hide this as `budget_exhausted` without
  distinction.
- **R3 Answer stability.** Relative operands are resolved against a
  reference date rounded down to `reference_date_granularity`. Within that
  window an identical question returns the identical (cached) disclosure.
  This stops the "flip-day" attack: asking "valid for more than 6 months?"
  daily and noting the day the answer changes would otherwise reveal the
  exact expiry date. With weekly rounding, the attack learns the week.
- **R4 Overlap and differential detection.** For ordered attributes,
  Gatekeeper keeps, per requester, the set of values consistent with all
  disclosures that requester has received. Before answering, it checks
  whether *any* possible answer to the new question would shrink that set
  below the minimum width for the attribute's sensitivity (e.g. one month
  for `high` dates). If so, it refuses with `overlap`. This also catches
  differential pairs such as `gt P6M` followed by `gt P5M` once those
  operands are allowed.
- **R5 Simulatable refusals.** Following Kenthapadi, Mishra and Nissim, an
  auditor is simulatable if the attacker, knowing the query-answer history,
  could make the same decision about whether a new query will be answered;
  such refusals provably leak nothing. R4 is simulatable because it ranges
  over all possible answers and uses only the requester's own history,
  never the true value. Using other requesters' histories in R4 would break
  this property for non-colluding requesters, which is why cross-requester
  protection is limited to the data-independent counters of R2.
- **R6 Attack test suite (planned).** An open suite of scripted attackers
  (binary search on a date, threshold walking, flip-day, multi-requester
  collusion) with the measured leak per attribute as the benchmark. Claims
  of protection are made against the suite, not in general.

For general query classes, exact auditing is computationally hard (the
literature reports NP-hard and coNP-hard cases, see Kenthapadi et al. § 2).
Gatekeeper restricts the language (§ 3) to cases where R1–R5 are cheap and
their effect is measurable.

- K. Kenthapadi, N. Mishra, K. Nissim. *Denials leak information:
  Simulatable auditing.* Journal of Computer and System Sciences 79 (2013)
  1322–1340; preliminary version at PODS 2005.
  <http://theory.stanford.edu/~nmishra/Papers/denialsLeakInformation.pdf>
- S. U. Nabar, B. Marthi, K. Kenthapadi, N. Mishra, R. Motwani. *Towards
  Robustness in Query Auditing.* VLDB 2006.
  <https://www.vldb.org/conf/2006/p151-nabar.pdf>
- N. R. Adam, J. C. Wortmann. *Security-control methods for statistical

## 9. Proof plugins

Without a proof, a disclosure is a statement by the person's device, not
evidence. A proof plugin attaches evidence when a recipient needs it.

Interface (language-neutral):

```
ProofPlugin
  id                         e.g. "sd-jwt"
  canProve(disclosure, attestation) -> bool
  prove(disclosure, attestation, recipientBinding) -> Proof
Proof
  format                     e.g. "sd-jwt"
  value                      opaque string (format-specific)
```

- `attestation` is issuer-signed material the host app holds (e.g. an
  SD-JWT credential). `recipientBinding` carries the requester's audience
  and nonce for replay protection.

Rules:

- PR1. A proof MUST NOT reveal more than the disclosure it accompanies.
  If the only available proof would reveal the attribute value, the plugin
  MUST report `canProve = false`; Gatekeeper then returns the disclosure
  without a proof, never a weaker one.
- PR2. Plugins MUST use existing, audited libraries. Gatekeeper defines no
  cryptographic primitives of its own.
- PR3. Proof generation runs after step 8 of arbitration and is logged in
  the same entry.

**First plugin: SD-JWT** ([RFC 9901](https://www.rfc-editor.org/rfc/rfc9901.html)).
SD-JWT lets a holder reveal selected issuer-signed claims, with key binding
to a recipient. It can prove a predicate only if the issuer signed that
predicate as a claim (for example an age-over claim). For predicates the
issuer did not anticipate, PR1 forbids falling back to disclosing the
underlying claim. Range proofs over arbitrary values need zero-knowledge
techniques; candidate libraries are a later feasibility study, not part of
v0.1. Functional and predicate encryption are research directions only.

## 10. Security considerations

- **Correctness of data.** Gatekeeper answers from the host app's data.
  `source: self_declared` data yields self-declared answers. Requesters
  needing assurance must ask for a proof (§ 9).
- **Requester identity.** Budgets and policies are only as strong as the
  binding of `requester_id` (e.g. an MCP OAuth client registration). A
  requester able to mint new identities could bypass per-requester budgets;
  per-attribute budgets (R2) bound this.
- **Purpose is a claim.** Gatekeeper records and binds purpose; it cannot
  verify it. The consent UI must make this clear to the person.
- **Prompt injection.** An injected agent may ask unexpected questions.
  Default deny, closed operands and budgets bound the damage to what the
  person approved.
- **Time.** R3 depends on the device clock. A manipulated clock can shift
  the reference date; implementations SHOULD refuse relative questions if
  the clock moves backwards relative to the last log entry.
- **Timing and errors.** Refusals are decided before the data is read
  (A1), so their timing cannot depend on the data. Evaluation (step 7)
  SHOULD run in time independent of the value where practical.
- **Denial of service.** A requester can exhaust cross-requester budgets
  and starve others. Open question (§ 11).
- **Consent fatigue.** Standing, purpose-bound policies with expiry are
  preferred over per-question prompts; the person can always review the
  log and revoke.
- **Audit log tampering.** See L2: tamper-evident, not tamper-proof,
  against an attacker controlling the device.
- **Fail closed.** Every failure path ends in a refusal (A3, § 7 step 8).

## 11. Open questions

1. Minimum widths for R4 per sensitivity level: fixed defaults, or set by
   the person at consent?
2. How to protect against cross-requester denial of service without making
   refusals depend on other requesters' activity.
3. Whether `unknown` should be a disclosure or a refusal for attributes
   whose absence is itself sensitive.
4. Multi-attribute questions (e.g. "valid permit *and* work allowed?"):
   excluded in v0.1 (Q2); can they be admitted without losing R4?
5. Format for policy proposals sent by requesters, and how they map onto
   MCP authorization and elicitation.
6. Canonical encoding of the question for overlap detection when operands
   are equivalent but written differently (e.g. `P6M` vs `P182D`).
7. Which proof formats beyond SD-JWT are mature enough for a plugin.
8. Where the specification should be maintained in the long term (an open
   standards or community group).
